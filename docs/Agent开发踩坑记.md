# 报错说"网络断了"，真凶是半个 emoji——我自研 AI 编码 Agent 半年踩的 7 个坑

今年 6 月起，我开始给自己造一个 AI 编码工具：类似 Claude Code 的形态——在终端里跟大模型对话，它能读我的代码、改文件、跑命令、自己多轮干活，底层接的是 DeepSeek 的 API。到今天 359 次提交里，有 129 次是在修 bug。

做了半年最大的感受是：**agent 开发的坑，大多不在"模型不够聪明"，而在工程接缝上**——模型没问题，是我的代码在中间把事情搞坏了。而且这些坑有个共同点：症状离奇，真相朴素。

从踩坑台账里挑 7 个最典型的，每个都把当时的排查过程和解法写清楚，希望后人少绕路。

---

## 坑 1：一次"网络故障"，其实是 emoji 被劈成了两半

**现象**：某天开始，一个会话每次发消息都报 400 错误，措辞是 `unexpected end of hex escape`（十六进制转义意外结束）。这看着像什么？像请求被网络截断了。我一度以为是代理或网络的问题。

**排查**：越查越不对劲。磁盘上的会话文件干干净净、内容完整；同样的内容上一个进程还发送成功过；重试一百次也是同一个错。扫文件什么都扫不出来。

**真相**：为了让上下文不超长，我的代码会把旧消息截断到 500 字符。问题就出在切这一刀上——emoji 在 JavaScript 内部占**两个存储位**（叫"代理对"），这一刀恰好从中间切下去，剩下**半个 emoji**。这半截残骸被序列化成 `\ud83d` 这样的孤立转义，DeepSeek 的服务器一看：不认识，拒收。

也就是说：不是网络断了，是**货在打包的时候被我切坏了**，报错文案却把嫌疑指向了运输队。

**解法**：
1. 所有按长度截断的地方，改用一个"防劈"函数——切之前检查切点是不是半个代理对，是就把切点往前/往后挪一位；
2. 在发请求的出口处再加一道终防线：发送前自动清扫消息里的孤立残骸。这样就算未来某个新切点漏了防劈，毒也出不了门。

**教训**：报错文案也是一种"转述"，不是事实陈述。先在本地把坏数据复现出来，再下结论。

## 坑 2：缓存是"整箱"结算的，一个字节不对，全箱按原价重买

**背景**：DeepSeek 有前缀缓存机制——对话开头的固定部分（工具说明书 + 系统提示词）如果和上次一模一样，命中部分只收约 1/50 的价格。省不省钱全看它。

**实测**：我做了四组对照实验才发现，缓存的最小结算单位**不是逐字前缀，而是一整块**：前面约 1.1 万 token 的固定内容被打包成一个整体。这块里哪怕只差一个字节——比如系统提示词尾部注入的"回复语言"变了、技能目录刷新了——**整块全部作废，按原价重算**。

就像超市整箱优惠：你可以只喝一半，但只要拆过封，就不算整箱价了。

**解法/原则**：
- 需要稳定的部分严格钉死：目录列表按名字排序（别依赖文件系统返回顺序）、注入内容做到字节级一致；
- 会变的东西（用户消息、工具结果）全部放到块的**后面**去，永不混进前缀。

改完之后，同一台机器上重跑同一个问题，缓存命中率从真实的 ~15% 提到 99.8%。

## 坑 3：并行派 20 个小助手，20 张账单全是原价

**现象**：某天一个任务并行派了 20 个子代理（agent 里干杂活的分身），当天成本暴涨，一查账：这 20 个分身的缓存命中率全是 **0%**，一个 token 都没省。

**真相**：每个子代理的系统提示词（相当于"自我介绍"）里写了各自的**任务内容**。20 份自我介绍互不相同 → 20 个前缀互不相同 → 缓存互相不命中，全部按原价买单。我自己亲手把缓存给搅了。

**解法**：自我介绍改成**统一模板**——所有子代理的开头逐字节一致（身份、规范、铁律）；任务描述、角色补充这些"各不相同的东西"全部挪到第一条用户消息里去。

改完同类子代理能互相命中，每个子代理首轮省下约 1.5 万 token 的重复计算。

## 坑 4：工具"永远转圈"，不是模型死了，是我忘了喊"干完了"

**现象**：界面上某个工具一直显示"运行中…"，对话像死机，怎么等都没下文。

**真相**：有两类特殊工具（进出计划模式）不走正常执行流程。我在它们开始时发出了"开始了"的信号，但结束时**忘了发"结束了"的信号**。前端是个老实人：等不到结束信号，就一直转圈。

这只是开头。这类"卡死/没输出"我前后一共修了七种，症状几乎一样，根因各不相同：有信号漏发的、有出错信息被去重逻辑吞掉的、有会话恢复时消息对不上账的、有超时重试的条件永远不满足的。

**排查心得**：agent 的"静默故障"大多不是模型的问题，是**事件流的缺口**——流水线上某个环节忘了说话，下游就干等。遇到"卡死"，先查是不是哪句话没喊出来，别急着怪模型。

**解法**：补齐信号只是表层，根治靠三件套——出错路径必须有兜底 catch（任何异常都要给用户一个交代）、会话恢复时对账补占位、状态复位放进 finally（保证失败路径也执行）。

## 坑 5：给工具穿了件马甲，模型看到的是个空盒子

**现象**（同一个坑踩了三次之后，我立了铁律）：命令明明执行成功了，模型却一口咬定"失败了，没看到退出码"。

**真相**：我想给某个工具加一道安全检查，就给它包了一层壳。但这个工具是"流式"的——一边执行一边往外吐结果；而壳写成了普通函数。框架一看外壳不是流式的，就把里面的产物整个"装箱"，装出来一个空盒子 `{}`。模型拿到的只有空盒子，自然以为命令什么都没干。

**解法**：壳本身也必须声明为流式（`async function*`），并且用 `yield*` 把里面的产物**原样转发**出去，一个字节都别截留。

第三次踩完，我把这条写成了守门测试：以后谁再写出"普通函数包流式工具"的代码，测试直接红。

## 坑 6：跑测试随机挂，凶手是"往屏幕上打了中文"

**现象**：全量跑测试时随机挂，每次挂的文件还不一样；单独跑失败的文件，又是全绿的。纯玄学。

**真相**（查了一整天，最后发现是 node 本身的 bug）：node 的测试框架用**同一条管道**传两类东西——子进程往屏幕上打印的文字、测试结果的二进制消息。二进制消息开头标着"这条消息有多长"，而打印中文时（UTF-8 的中文字节 ≥ 0x80）这个长度就被读歪了，整条管道的解析全乱套。失败文件随机 = 谁碰巧和中文输出挤在同一批，谁挂。

这是 node 的已知 bug（[nodejs/node#64061](https://github.com/nodejs/node/issues/64061)），v22 没有修复。

**解法**：跑测试前预载一段小脚本，把子进程打印出来的中文转成 `\uXXXX` 转义（只转 stdout，报错通道不动）。治标，但稳。等 node 上游修了就拆掉，我在台账里挂了账。

## 坑 7：本地全绿 ≠ CI 绿，白板机器专治"我机器上没问题"

**现象**：本地测试全过，一推 GitHub，CI（自动测试）就红，还换着花样红。

**真相**：CI 的运行机器是一台"白板"电脑——上面没有我本机的任何配置。两个经典案例：

- 测试里建临时 git 仓库，一提交就报"不知道你是谁"——因为 CI 机器没配 git 的用户名邮箱，而我本机有全局配置，**这类 bug 本地永远复现不出来**；
- CI 机器的临时目录是 Windows 老式的 8.3 短文件名（`RUNNER~1` 这种），同一个文件夹有两个名字。我的代码拿"环境变量里的路径"和"解析后的真实路径"做前缀比较，就误判了。

**解法**：测试自己动手把仓库级 git 身份配齐，不依赖环境；所有路径比较之前，两边都先转成真实路径再比。

**教训**："本机能跑"不算数。我的规矩是：每次推送后盯着 CI 跑完才收工，红了当场修——因为白板机器暴露的，往往是真实用户机器上也会有的环境差异。

## 写在最后
